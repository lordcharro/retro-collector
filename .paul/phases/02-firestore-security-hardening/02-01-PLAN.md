# Phase 02 — Plan 01: Firestore Security Rules & Production Authentication Hardening

## 🎯 Objective
Transition Cloud Firestore from expiring 30-day "test mode" to **Production Mode** by:
1. Authoring and deploying hardened, schema-validating **Firestore Security Rules (`firestore.rules`)** that strictly whitelist `/games/{gameId}` and `/chat_threads/{messageId}`, validate every field type/enum/size bound, and deny all other paths (preserving the rule that `AppSettings` never touches Firestore).
2. Integrating multiplatform **Firebase Authentication (REST API)** using the existing `firebaseApiKey` in local `AppSettings`, attaching `Authorization: Bearer <idToken>` headers to all `FirestoreService` requests.
3. Exposing the **Firebase Web API Key** field in `SettingsDialog` (`SettingsFirebaseSection`) so users can configure and test authenticated production access across Desktop, Android, and Wasm.

---

## 🛡️ `<boundaries>` & Clean Architecture Enforcement

- **The Dependency Rule**:
  - `..domain..` depends on **nothing** (`domain.dependsOnNothing()` in `CleanArchitectureKonsistTest`).
  - `..domain..` and `..domain.usecase..` MUST NOT import `io.ktor.*`, `kotlinx.serialization.json.JsonObject`, platform SDKs, or UI frameworks.
  - `..domain.repository..` MUST contain **interfaces only** (zero concrete classes).
  - All `UseCase` classes MUST reside in `..domain.usecase..` and define `operator fun invoke(...)`.
- **Storage Invariants**:
  - `AppSettings` (`firebaseProjectId`, `firebaseApiKey`, etc.) is persisted **strictly locally** (`SharedPreferences` on Android, `~/.retrocollector/settings.json` on Desktop).
  - **NEVER** save, sync, or create a Firestore collection/schema for `AppSettings`.
  - Cloud Firestore is exclusively dedicated to `games` and `chat_threads`.

## ✅ Acceptance Criteria (Given / When / Then)

### AC-1: Production Firestore Security Rules Validation (`firestore.rules`)
- **Given** a Firestore database configured with `firestore.rules` in Production Mode
- **When** an authenticated client writes a valid `GameItem` document to `/games/{gameId}` or a valid `ChatMessage` to `/chat_threads/{messageId}`
- **Then** the write is permitted if and only if the client passes `isAuthenticated()` and all fields conform to the `hasOnly` whitelist, enum constraints, and size bounds; any write to any other collection (such as `settings` or `users`) or any unauthenticated request is rejected with `PERMISSION_DENIED`.

### AC-2: Authenticated Firestore REST Requests via `FirebaseAuthService` & `FirestoreService`
- **Given** `firebaseProjectId` and `firebaseApiKey` are configured in local `AppSettings`
- **When** `FirestoreService` executes `getGames`, `saveGame`, `deleteGame`, `getChatMessages`, `saveChatMessage`, or `deleteChatMessage`
- **Then** `FirebaseAuthService` exchanges the `firebaseApiKey` for a valid Firebase ID token (or reuses/refreshes a cached token) and `FirestoreService` attaches `Authorization: Bearer <idToken>` to the HTTP request.

### AC-3: Local-Only Settings Persistence & UI Configuration
- **Given** the user opens `SettingsDialog` on Desktop, Android, or Wasm
- **When** the user enters their `firebaseProjectId` and `firebaseApiKey`, clicks **Test Connection**, and saves settings
- **Then** the connection test authenticates via `FirebaseAuthService` and verifies read access against `/games`, while `firebaseApiKey` and `firebaseProjectId` are persisted strictly in local storage (`AppSettings`) and never transmitted as a document to Cloud Firestore.

### AC-4: Clean Architecture & Konsist Compliance
- **Given** all Phase 02 code modifications
- **When** `CleanArchitectureKonsistTest` is executed
- **Then** all architectural assertions pass with zero violations (`domain.dependsOnNothing()`, `domain.repository` contains only interfaces, `UseCase` classes reside in `..domain.usecase..` with `invoke` operator).
